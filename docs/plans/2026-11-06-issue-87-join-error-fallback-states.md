## Acceptance criteria

From the issue:
1. None of the four inputs (siteverify non-JSON 5xx, siteverify network failure, POST with no body or a non-form content type, rejected token) produces an uncaught exception. Each returns an HTML page with a route forward: a `/join` link, a home link and the contact email.
2. With `challenges.cloudflare.com` blocked, or with JS off, `/join` shows an explanation and the contact email within a few seconds.
3. A token whose `hostname` is not `gatewaysmash.com` or `www.gatewaysmash.com` is rejected.
4. `npm test` runs Worker tests, and CI fails when one is broken (negative-tested, per CLAUDE.md).

From the orchestrator:
5. The invite URL leaves only through the 302 after a verified token, and never appears in an error page, a log line or a test fixture. Failure paths fail closed. No detail from Cloudflare's error response reaches the visitor.
6. `npm test` passes with `worker/node_modules` absent. Worker tests are dependency-free `node --test`.
7. Local development works with Cloudflare's test keys, and no configuration value can widen the production hostname list.
8. Unexpected methods return 405 rather than the challenge page or an exception. A non-form POST also returns 405, as the issue specifies.
9. Every HTML response goes through one small helper, so #91 has one place to add headers. The security headers are not added here.
10. CLAUDE.md, worker/README.md and the root README are correct afterwards, and the PR says plainly that merging does not deploy the Worker and which command the user runs.

## Design

### Hostnames: a dev entry point, not a variable

`worker/src/index.js` holds `SITE_HOSTNAMES = ['gatewaysmash.com', 'www.gatewaysmash.com']` as a constant and reads nothing from `env` for it. The handler takes it as a defaulted fourth parameter:

    async fetch(request, env, ctx, allowedHostnames = SITE_HOSTNAMES)

The Workers runtime passes three arguments, so production always gets the constant.

New `worker/src/dev.js` (about 6 lines plus a comment) wraps it and adds `example.com`:

    import gate from './index.js';
    export default {
      fetch: (request, env, ctx) =>
        gate.fetch(request, env, ctx, ['gatewaysmash.com', 'www.gatewaysmash.com', 'example.com']),
    };

`worker/package.json`: `"dev": "wrangler dev src/dev.js"`. `wrangler.toml` `main` stays `src/index.js`, and `deploy` stays `wrangler deploy`, so `dev.js` is never reachable from a deployed bundle: `index.js` imports nothing. No `[vars]`, secret or dashboard value can widen production, because there is no such setting. Getting the loose list deployed takes a deliberate `wrangler deploy src/dev.js`. Running plain `wrangler dev` fails closed with the 403 page, which also makes it the local way to prove the production check rejects a test token.

Rejected: a `[vars]` or `.dev.vars` flag (a dashboard or config value could loosen production), and keying on `request.url` being localhost (wrangler dev can rewrite the URL to the first route's host, so it is unreliable, and it still puts dev logic in the production path).

`index.js` deliberately has no named export: only the default export object reaches the runtime, and the handler's parameter is all dev.js needs.

### Handler shape (`worker/src/index.js`, one file)

- `fetch`: whole body in `try`. GET and HEAD return the challenge. POST returns `await verify(...)`. Anything else returns the failure page at 405 with `Allow: GET, HEAD, POST`. `catch (error)`: `console.error('join-gate: request failed', error?.name)` (optional chaining, so a thrown non-object cannot throw again inside the catch) (the name only, never `error.message` and never a Response body) and return the 502 page.
- `verify`:
  1. Content type must match `/^(application\/x-www-form-urlencoded|multipart\/form-data)\b/i`, else 405. A missing header is `''` and also 405. Both 405 sites send `Allow: GET, HEAD, POST`, from one `ALLOW` constant, because a 405 without it is what review found here.
  2. `request.formData()` in its own `try`; on a throw (malformed multipart) return the 405 page at status 400.
  3. `token = form.get('cf-turnstile-response')`. If it is not a non-empty string (a File is possible in multipart), return 403 without calling siteverify.
  4. If `env.TURNSTILE_SECRET` or `env.INVITE_URL` is unset, return 502 (otherwise the old code would send `Location: undefined`).
  5. siteverify `fetch` as today, plus `signal: AbortSignal.timeout(10000)`, so a hung Turnstile does not hang the visitor. A throw lands in the outer catch as 502.
  6. `await verify.json()`: non-JSON lands in the outer catch as 502. `verify.ok` is deliberately not consulted, because a rejected token can legitimately be a non-200 with a JSON body; only the parsed result decides.
  7. Pass only when `result.success === true && allowedHostnames.includes(result.hostname)`: return the 302 (`Location: env.INVITE_URL`, `Cache-Control: no-store`). Anything else is the 403 page. `error-codes` is never read or echoed.

- `html(body, status = 200, headers = {})`: the single helper for every HTML response. It sets `Content-Type: text/html;charset=UTF-8` and `Cache-Control: no-store`. #91 adds headers here. The 302 is not HTML and stays separate.
- `shell(title, body)`: the shared document (doctype, `lang`, charset, viewport, `noindex`, title, the existing `<style>` plus a small `max-width` and `box-sizing`, a head-slot argument for the Turnstile script tag). The body is wrapped in `<main>`, because the body is a centring grid and loose children would each become a row stretched across `100vh`; `max-width` goes on `main`. Every page gets the same `noindex`.
- `failure(status, heading, message, headers)`: returns `html(shell(...))` with the h1, the message, a `Try again` link to `/join`, the home link, and the contact line.
- Pages contain only constants and `env.TURNSTILE_SITEKEY`. Nothing from the request or from Cloudflare is interpolated.

### Challenge page

    <h1>Join the WhatsApp group</h1>
    <form id="f" method="POST" action="/join">
      <p>Quick check, then you'll be sent to WhatsApp.</p>
      <div class="cf-turnstile" data-sitekey="..." data-callback="done"
           data-error-callback="showHelp" data-expired-callback="showHelp" data-timeout-callback="showHelp"></div>
    </form>
    <p id="help" role="status" hidden>...</p>
    <noscript><p>...</p></noscript>
    <p><a href="/">Back to Gateway Smash</a></p>
    <script>
      var solved = false;
      function done() { solved = true; document.getElementById('f').submit(); }
      function showHelp() { document.getElementById('help').hidden = false; }
      setTimeout(function () { if (!solved) showHelp(); }, 4000);
      window.addEventListener('pageshow', function (event) { if (event.persisted) location.reload(); });
    </script>

The 4-second timer is what catches a blocked `api.js`: no callback can fire if the script never arrived, and a blocked request does not always fail fast. It keys on no token having arrived, not on `window.turnstile`: a cached `api.js`, or a block on the iframe alone, sets `window.turnstile` while the check still cannot run, and the first version left that visitor with no help for 43 seconds, until Turnstile's own timeout. Setting `solved` in `done()` keeps help hidden while a solved form waits on a slow siteverify. Help can now appear beside a slow but working widget, which is harmless, and is why its first sentence is `Still waiting?` rather than a claim that the check failed. `showHelp` returns nothing, so the widget keeps its own retry behaviour. The `pageshow` listener exists because Back after `done()` can restore `/join` from the back/forward cache with a solved widget, no way to resubmit and `#help` hidden; reloading gets a fresh widget. No inline event-handler attributes, because #91's CSP should not have to allow them.

### Copy (verbatim; Copy style: sentence case, straight quotes, no em dashes)

- `CONTACT` line, shared: `Still stuck? Email <a href="mailto:info@gatewaysmash.com">info@gatewaysmash.com</a>.`
- help: `Still waiting? A content blocker or a school or work network can stop this check. Turn the blocker off or try another network. Still stuck? Email <mailto>.`
- noscript: `This check needs JavaScript. Turn it on and reload this page. Still stuck? Email <mailto>.`
- 403: heading `That check didn't pass`, message `It may have timed out. Try it again.`
- 502: heading `We couldn't run the check`, message `The check service didn't answer, so nothing went wrong on your side. Try again in a minute.`
- 405 and 400: heading `That request didn't work`, message `Start again from the join page.`
- Links: `Try again`, `Back to Gateway Smash`.

The address is one `EMAIL` constant in `index.js`.

## Tests

Stub `globalThis.fetch`, call `worker.fetch(request, env)`, assert on the Response. Restore the stub in `afterEach`. The fixture invite is a sentinel, `https://invite.example.invalid/sentinel`, and the secret is a sentinel too. Never a real invite.

`defects.test.js` (frozen) proves only what the issue reported, and asserts structure rather than copy: status, `text/html` content type, `href="/join"`, `href="/"`, `mailto:info@gatewaysmash.com`, and no `Location` header.
- siteverify 503 with an HTML body: 502 page.
- siteverify fetch rejects: 502 page.
- POST with no body and no content type: 405 page.
- POST with `application/json`: 405 page.
- Rejected token: 403 page, HTML instead of plain text.
- `success: true`, hostname `evil.example`: 403, no redirect. Same with hostname absent.
- Challenge page: has an `h1`, a home link, a `<noscript>` holding the mailto, a `hidden` block holding the mailto, and a `data-error-callback` naming a function the inline script defines.

`gate.test.js` (unfrozen):
- 302 with the right `Location` and `no-store` for each of the two hostnames, urlencoded and multipart.
- `success: "true"` (string) rejected.
- Failure pages never contain the invite or the secret, and `console.error` output does not either (stub it and collect the arguments), across all failure paths including a siteverify body that echoes the secret.
- Cloudflare `error-codes` text does not reach the page.
- Empty token and a File token: 403 and siteverify not called.
- Missing `INVITE_URL` or `TURNSTILE_SECRET`: 502, no `Location`.
- Malformed multipart: 400 page.
- PUT, DELETE and OPTIONS: 405 with `Allow`. HEAD: 200.
- Mixed-case content type accepted.
- `signal` is passed to siteverify, and an `AbortError`-style rejection gives 502.
- Every HTML response carries `text/html`, `no-store` and `noindex`.
- `dev.js` accepts `example.com` and still rejects `evil.example`; `index.js` rejects `example.com`.
- `wrangler.toml` has `main = "src/index.js"`, and `worker/package.json` `deploy` is exactly `wrangler deploy`. These two lines are what keep `dev.js` out of production, so they are the one thing a text read must pin.
- The address in the Worker's pages equals the `mailto:` in the root `index.html`.
- Reads every file under `worker/src` and `worker/test` and fails on an invite-shaped URL (`chat.whatsapp.com` or `wa.me/`). The test's own regex is written with escapes so it does not match itself. Negative-test it with a temporary fixture line.

## Risks

- `request.formData()` differs between Node's undici and workerd. The live drive repeats each POST case through real workerd, so the unit tests are not the only evidence.
- `wrangler dev src/dev.js` is unproven until run. If wrangler refuses, use `wrangler dev --config` with a dev-only config, edit this plan in the same commit, and keep the property that nothing deployed can name dev.js.
- `.dev.vars` overriding `[vars]` for `TURNSTILE_SITEKEY` is assumed. Verify, because the README relies on it.
- Tightening method handling: POST and GET are the only methods the site uses, so a 405 on others affects nobody. HEAD stays 200.
- Fail-closed cost: during a Turnstile outage nobody joins through `/join`. The email fallback is the mitigation, and that is the intended trade.
- Worker changes do nothing until the user deploys. The PR must say so.

Chosen not to do: security headers (#91), rate limiting, siteverify retry, `idempotency_key`, `action` or `cdata` checks, styling to match the site.
